Session Plan

Session 37: Colours chosen directly

Why. Palettes are more than a designer needs (operator, 2026-11-08): many systems stay black, and a colour-blind variant is simply a second config.

  1. Register.
  2. A notehead's colour is chosen on the notehead (or its rule) and carried there; the config has no palette to fill. Palettes become suggestions a designer can apply from help, colour-blind-safe sets among them.
  3. The colour-blind alternative and the export's accessible-colour branch go: a variant is a config saved under another name (session 36's save dialog). The exporter registers the colours the noteheads use. No engine change: cnb:use-accessible-colors is simply never set.
  4. A config with a palette still loads, its colours moved onto the noteheads, so it previews and exports as before. The baselines and the LY spec say what changed.

Work Plan

Session 37 moves colour from the palette onto the noteheads. Item 1, registration, was done when the session started. A notehead's colour is a notehead rule's apply.color. The look-table inference writes colour as rules, the way it writes shape, fill, size and side step, and null now means none (black). The config loses its palette: createDefault has none, CNBConfig.resolveColor and the palette validation go, and the preview draws the resolved colour or black. A config that still carries a palette is converted when it loads (new CNBConfig.paletteToRules, called by CNBConfigIO.mergeLoaded), so it previews and exports as before. Its primary colours become colour rules below every existing rule, so explicit rule colours still win. Explicit color:null fields are dropped, and the palette and its colour-blind set go. The colour-blind alternative goes everywhere: the notehead panel's twin field, palette.useCBSafe, engine.useAccessibleColors and its editor row, and the export's cnb:use-accessible-colors branch. A colour-blind variant is a config saved under another name with session 36's save dialog. The Advanced › Colour palette editor is retired. Its curated sets, colour-blind-safe ones among them, become suggestions in a help disclosure in the notehead panel's Colour group, which a designer can apply. The colour naming the exporter needs moves from the palette editor into cnb/src/cnb-color.js. The exporter then registers the colours the resolved noteheads use, unconditionally, named from their hex (nearestColorName → toSchemeSymbol), with no palette.schemeSymbols. The fixtures are converted, the five export baselines regenerated, the test pages and UAT drivers follow, and LY spec 1.3.10, the architecture plan, the README and CLAUDE.md say what changed.

Colour on noteheads

Make the notehead (its rules) the only place colour lives, and retire the palette editor. Module A (cnb/src/cnb-config.js) changes as follows. createDefault has no palette. resolveColor goes. The palette validation goes: palette hex checks, the CB-safe count warning, the 'no color rule and no palette' warning and the schemeSymbols check. The shared-position warning compares resolved colours. A new CNBConfig.paletteToRules(config) returns a config without palette. Its palette.colors primary entries (useCBSafe ignored: the primary colours are what the export engraves by default) become one rule per distinct non-black colour: matching that colour's pitch classes, every duration and key, apply {color}, placed below every existing rule with the existing order kept. Rules' explicit color:null fields are dropped. A config without a palette comes back unchanged. CNBConfigIO.mergeLoaded calls it, and REPLACE_PATHS loses palette.schemeSymbols. cnb-card.js and cnb-key-signature.js colour a notehead with the resolved colour, else black. notehead-inference.js reads colour from the owned rules and writes it as rules like the other attributes: the Default carries the default colour when there is one, each other colour gets a rule, and a none group gets {color:null}. It names colours with CNBColor.baseColorName and writes no palette. notehead-panel.js loses the colour-blind-safe twin field and the schemeSymbols writing. Its 'Start from a palette…' select becomes a 'Suggested colours' help disclosure in the Colour group. The disclosure says that a colour-blind version is the config saved under another name with other colours, and lists the curated sets (Dark2 and the colour-blind-safe sets, marked as such), each with its swatches and an Apply button that colours the twelve noteheads, cycling the set as the palette editor did, black as none. Delete cnb/ui/palette-editor.js, its tests and cnb/test-pages/test-palette-editor.html. Unit tests follow each change, including paletteToRules on the Kite fixture: every pitch class × duration resolves to the colour the palette gave it.
