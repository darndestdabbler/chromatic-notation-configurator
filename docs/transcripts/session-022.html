Session 22: Each notehead has its own height and width

Why. Every notehead is drawn at its shape's semitoneHeight, at the shape's natural aspect ratio. A palette of very different shapes may need different sizes to look right, and the operator asked (2026-11-06) that a notehead's height and width each be adjustable from 0.25 to 4 semitones: the extremes look wrong, but they let the user make whatever adjustment a design needs. The notehead-first editor (session 19) lists size among the things a click on a notehead sets, so the schema, preview and export built here are what that editor will drive. No engine change is needed: the engine has no size field and builds each stencil from the registered path's numbers in staff-space units, so the exporter can register a scaled variant of a shape per size.

  1. Register.
  2. Schema (cnb-config.js): a rule's apply block gains optional heightSemis and widthSemis, absolute sizes in semitones, resolved through the cumulative rule pipeline like hollow and xOffsetStaffSpaces. Absent means the shape's own semitoneHeight and its natural width, so every existing config resolves, previews and exports exactly as before (the preview and export baselines pin it). Validation: a present value must be a finite positive number (error); outside 0.25 to 4 semitones warns. Document the fields in the architecture plan §4.5 and the LY export spec.
  3. Preview: cnb-notehead.js measures with separate x and y scale factors from the resolved size; the stem anchors, the octave-pair offset (cnb-double-notehead.js), the ledger width derived from notehead width (cnb-ledger-set.js, cnb-card.js) and the key-signature marks (cnb-key-signature.js) all follow the resolved measurement. Unit tests in the file named after each changed source, and a visual check in cnb/test-pages/test-notehead.html.
  4. Export (cnb-lilypond.js): for each distinct resolved (shape, height, width) that differs from the shape's own size, Section A registers a variant under a derived name (the shape name with a size suffix), with its path, hollow cutout and attachment points scaled by the same x and y factors, and Section C points the pitch classes at it; the resolved size joins the Section C grouping key beside shape, hollow, colour, attachment and x-offset. The spec gains a section for the variant naming and scaling. Pin a sized export against a new baseline, and check the engraved sizes with an engine render through cnb/tests/engine-probe.js, as session 11's notehead-size test does.
  5. Editor (notehead-rule-editor.js): a rule's apply block gets height and width controls with a "keep aspect ratio" lock, on by default: with the lock on, editing the height rewrites the width at the shape's natural ratio; with it off, the width is free. The shape's natural width shows as a hint beside the field. Keep the controls minimal: the notehead-first editor (session 19) will supersede this panel. Record the browser check in docs/uat-status.md.
  6. README "Preview-only settings" and the gallery configs: say that size exports, and leave the fixtures' sizes untouched.

Work Plan

Give each notehead its own height and width. A notehead rule's apply block gains optional heightSemis and widthSemis (absolute sizes in semitones), resolved through CNBConfig.resolveNotehead's cumulative pipeline like hollow and xOffsetStaffSpaces (null when no matching rule sets it, meaning the shape's own semitoneHeight and natural width, each independently). Validation errors on a present value that is not a finite positive number and warns outside 0.25-4 semitones. In the preview, CNBNotehead.measure takes the resolved size and returns separate x and y scale factors; render draws scale(sx, sy) only when they differ, so an unsized config renders byte-identically (the preview and export baselines stay pinned unchanged). The card's stem anchors, ledger width (CNBCard passes the resolved width to CNBLedgerSet, which takes its width from the caller), column width and repeat-mode group, the octave pair (cnb-double-notehead.js) and the key-signature marks all follow the resolved measurement. The exporter registers, for each distinct resolved (shape, height, width) that differs from the shape's own size, a Section A variant named after the shape with a size suffix (-h<height>-w<width>, decimal point written as p), whose path, hollow cutout and attachment points are scaled by the same x and y factors; Section C points the pitch classes at the variant, and the size joins the grouping key. A sized fixture config is pinned against a new export baseline, and an engine-backed test (skipping without LilyPond, via cnb/tests/engine-probe.js) checks the engraved sizes. The notehead rule editor gets height and width controls with a keep-aspect-ratio lock, on by default, and a natural-width hint; the browser check goes in docs/uat-status.md. The architecture plan §4.5, the LY export spec (1.3.4, a section on variant naming and scaling) and the README's Preview-only settings section document that size exports.
